# Codebase Brain 使用指南

本文面向第一次接触 Codebase Brain 的开发者。日常使用时只需要向 AI 描述任务，不需要
记忆工具名或编排调用顺序。AI 应在计划或修改代码前自动调用统一入口获取上下文。

Windows 11 首次安装见 [`Windows安装指南.md`](Windows安装指南.md)。日常使用不需要
WSL、Linux、Docker 或 Hermes。

## 1. 它解决什么问题

普通 AI 编程助手主要依赖当前对话和它临时读到的文件。大型项目中容易出现：

- 不知道某个函数的调用关系和影响范围。
- 忘记团队约定，写出能运行但不符合项目规范的代码。
- 跨天任务丢失关键决策和踩坑记录。
- 不理解某段代码为何存在、最近改过什么、哪些文件通常一起改。
- 每次都从头扫描项目，耗时且浪费上下文。

Codebase Brain 把这些信息分成三层：

| 层 | 数据来源 | 作用 |
| --- | --- | --- |
| 结构层 | `codebase-memory-mcp` sidecar | 符号、调用链、依赖关系 |
| 团队知识层 | 约定 Markdown、会话记忆 | 告诉 AI 应该怎样改、以前为何这样决定 |
| Git 只读层 | Git blame、最近提交、共同变更 | 帮助判断历史原因和潜在影响文件 |

`brain_context_for_task` 会把多层结果整理成一个紧凑的 Context Pack，自动包含相关符号、
团队约定、历史会话、重点文件、最近变更、共同变更文件和 blame 样本。

## 2. 每天怎么用

### 开始任务和修改前

直接对 Qoder 描述目标：

```text
修复用户登录后偶发 500。先收集完整项目上下文并制定计划，不要立刻修改代码。
```

AI 应自动调用 `brain_context_for_task`，等待异步结果，并基于完整 Context Pack 制定计划。
如果任务描述不足以定位文件，可以补充文件名或符号名，但不需要手动调用 Git 工具。

复杂或跨天任务可以再说：

```text
调用 start_session 记录当前任务，任务描述为“修复用户登录后偶发 500”。
```

只有当 Context Pack 仍不足以解释某个具体符号或代码行时，AI 才应按需调用
`brain_explain_symbol` 或低层 Git 工具继续深挖。

### 修改过程中

遇到关键选择时：

```text
调用 record_decision，记录“保持现有认证中间件边界，不在视图层刷新 token”，
原因是“避免绕过统一审计和错误处理”。
```

解决了不明显的问题时：

```text
调用 record_problem，记录问题、根因、解决方案和相关文件。
```

完成一个重要文件修改后：

```text
调用 record_file_change，记录文件、修改类型和修改原因。
```

### 结束任务

```text
运行项目测试并总结结果。然后调用 end_session，保存本次任务的改动、关键决策、
未解决风险和后续事项。
```

## 3. 常用工具

| 场景 | 首选工具 |
| --- | --- |
| 计划或修改任何代码任务 | `brain_context_for_task` |
| 检查是否部署正常 | `health`, `brain_status` |
| 第一次使用项目 | `brain_index_project` |
| 代码改动后刷新图谱 | `brain_sync_status`, `brain_sync_project` |
| 理解函数、类和影响范围 | `brain_explain_symbol` |
| 查团队规范 | `search_conventions` |
| 继续以前的类似任务 | `recall_context` |
| Context Pack 后仍需深挖某段历史 | `get_recent_changes`, `get_blame` |
| Context Pack 后仍需扩大影响分析 | `get_co_changed_files` |
| 跨天保留任务上下文 | `start_session` 到 `end_session` |

## 4. 如何看返回结果

- `ok=true` 只表示调用成功，不表示内容一定完整。
- 先看 `status` 和 `warnings`。图谱 sidecar 缺失时，工具会降级返回本地知识。
- 语义搜索是相关性推荐，不是事实证明；重要结论仍需读取源码和运行测试。
- Git 共同变更表示历史相关性，不代表这次一定要一起修改。
- 异步工具返回 `queued` 后尚未完成，必须用 `brain_index_job_status` 查看最终结果。
- `brain_index_job_status` 的 `thread_alive=true` 表示后台线程仍在运行，`elapsed_seconds` 表示
  已运行时间；运行中每次轮询都会刷新 `updated_at`。
- 团队约定可能过期。发现冲突时先与代码所有者确认，再更新约定文件。

## 5. 不应该记录什么

不要向约定或会话记忆写入：

- 密钥、密码、token、连接串。
- 客户数据、生产日志、个人信息。
- 未经确认的猜测。
- 大段源码或无意义流水账。

好的记录应短、事实化，并说明原因。例如：

```text
决策：认证错误统一转换为 AuthError。
原因：API 中间件依赖该类型生成稳定错误码。
相关文件：auth/errors.py, middleware/auth.py
```

## 6. 团队约定怎么维护

约定文件位于业务仓库 `.codebrain/conventions/*.md`。它们应描述开发者需要遵守的规则，
而不是复制框架源码。

```markdown
---
module: auth
title: 认证错误处理
tags: [auth, errors]
---

认证模块向外返回 AuthError，不跨模块边界抛出底层数据库异常。
修改错误映射时必须补充 API 层测试。
```

约定由团队审核后提交。修改后调用 `index_convention_files`，让本机数据库重新索引。

## 7. 出现问题时

先让 AI 调用 `health` 和 `brain_status`，把 `status`、`warnings` 和错误文本交给维护者。
不要反复调用长任务；异步任务应轮询现有 `job_id`。Qoder 重启后 job 状态会丢失，需要重新发起。
